# SIGParser — Robustness TODO

SIGParser's architecture is sound: ANTLR grammar → semantic model (`Parsed`) →
jinja templates. That three-stage split is what mainstream codegen tools
(FlatBuffers, protobuf) use, and it is why a new output like `context_deps.h`
costs one template plus two accessors instead of surgery across the emitter.

What is missing is the **middle of a normal compiler front-end**: there is no
error detection, no source locations, and no validation pass. Everything below
is about that gap. Nothing here is a rewrite; the parsing design stays.

The unifying symptom: **a mistake in a `.sig` file does not fail the
generator.** It produces wrong C++, the generator reports success, and the
error surfaces later as a compile error in `autogen/` — or, worse, as behaviour
that is silently wrong. Every item below shortens the distance between a
mistake and the message about it.

## 1. Syntax errors are not detected (highest value)

`parse()` (`Parsing.cpp:507`) installs no error listener and never checks
`parser.getNumberOfSyntaxErrors()`. ANTLR's default listener prints to stderr
and then **recovers** — so a malformed `.sig` parses partially, the listener
walks a half-built tree, and the generator writes output from an incomplete
model and exits 0.

This is the worst failure shape in the tool: the output looks plausible, the
run looks successful, and the damage is discovered later somewhere unrelated.

**Do:**

- `lexer.removeErrorListeners()` / `parser.removeErrorListeners()`, install a
  custom `BaseErrorListener` that records file, line, column, and message.
- After the walk, if any errors were recorded, **fail the whole run** — do not
  write a single output file. Partial regeneration of `autogen/` is worse than
  no regeneration, because the tree is then internally inconsistent and the
  next person's `git diff` is noise.
- Return a non-zero exit code so `generate_sigs.bat` / CI can detect it.

Roughly ten lines, and it is a prerequisite for taking anything else here
seriously.

---

## 2. No source locations

`getLine()` / `getCharPositionInLine()` appear nowhere in `Parsing.cpp`. ANTLR
hands these out for free on every token and they are discarded.

`have_name::source_file` stamps the owning `.sig` path onto top-level items
(`Main.cpp`, in the `tag()` lambda), which is enough for an
"autogenerated-from" comment but not enough to point at a mistake.

**Do:** add `line` / `column` to `parsed_type` (it is already the universal
base) and fill them in the listener from `ctx->getStart()`. Every diagnostic in
items 3–5 is blocked on this; doing those first without locations produces
error messages that say *what* is wrong but not *where*, which in a 14-file
`sigs/` directory is barely better than nothing.

---

## 3. No validation / resolve pass

Nothing checks that names resolve. Concrete holes, all currently silent:

- A `[SetupCondition]` naming a struct that does not exist. `render_expr`
  (`Main.cpp:137`) passes an unknown `Owner::name` straight through as
  `Owner::name`, on the assumption it is a `Constants::` entry or a C++
  namespace. A typo'd context name is indistinguishable from that and becomes a
  C++ compile error in `pass_defaults.cpp`.
- A condition naming a *field* that does not exist on a struct that does. Same
  outcome.
- `[Always]` / `[Size]` / `[Format]` / `[Recreate]` referring to a field the
  pass does not declare.
- A `Pipeline` entry naming a `PassNode` that does not exist.
- An option name that is simply misspelled (`[SetupConditon = ...]`) — it is
  accepted, stored, and then never read by any template, so the pass silently
  loses its condition and runs unconditionally. **This one can change rendering
  behaviour without any compile error at all.**

**Do:** add a `validate(Parsed&)` between `parsed.setup()` and codegen in
`main()`. Walk passes, views, tables and pipelines; resolve every name against
`parsed.tables` / `parsed.enums` / `parsed.passes` / pass params; collect
diagnostics with locations; fail the run on any error.

A known-option-names whitelist per declaration kind is the cheapest high-value
part of this, and catches the misspelling case above.

## 4. `get_elem<T>()` relies on an unwritten invariant

```cpp
template <class T> T& get_elem()
{
    parsed_type* e = elems.back().elem;
    return *dynamic_cast<T*>(e);   // Parsing.cpp:70 — unchecked
}
```

Correctness depends on the top of the element stack happening to support the
trait a leaf listener wants. There is no check: if it does not, this is a null
dereference.

The trait-mixin design (`have_name`, `have_expr`, `have_owner`, …) is a genuine
strength — it is why `enterName_id` works identically inside a `Table`, a
`Pass`, a `PSO` and a `ValueAtom`, and why `Parsing.cpp` is under 500 lines for
a language this size. The problem is only that the invariant it rests on is
invisible.

Observed cost: adding `enterCond_term` required manually tracing
`GENERATE(Option)` → `GENERATE(Options_assign)` to confirm that `elems.back()`
would be the `ValueAtom` and not the `option`. That reasoning should be
mechanical.

**Do (cheapest first):**

- `assert(dynamic_cast<T*>(e))` with the rule name in the message. Turns a null
  deref into a locatable failure.
- Better: have `get_elem<T>()` walk *up* the stack for the nearest `T` instead
  of only inspecting the top. That makes the listener forgiving of grammar
  nesting changes rather than silently fragile — today, inserting one wrapper
  rule into the grammar can break leaf listeners that used to work.

## 5. Grammar looseness

Not breaking anything today; all of it is latent.

- **`value_id` alternative order** (`SIG.g4:129`) lists `ID` before
  `function_id`, so a bare identifier wins over a call. This is why `cond_term`
  has to list `function_id` ahead of `value_id` explicitly — otherwise
  `exists(X)` parses as an identifier followed by stray parentheses. Reordering
  `value_id` itself would remove the trap, but needs checking against every
  existing option that relies on the current order.
- **Non-greedy `option_block*?`** appears 16 times. A non-greedy subrule in a
  parser grammar usually means an ambiguity is being suppressed rather than
  expressed. Worth understanding why it was needed; it may be masking a real
  ambiguity that will surface as a confusing parse later.
- **`cond_op` (`SIG.g4:66`) has no arithmetic.** Only boolean/comparison
  operators and parentheses. See item 6.

## 6. `[Size]` expressions are still opaque

Conditions are fully structured, so `context_deps.h` can prove the field
dependencies of every pass's *enable* decision (`deps_complete` is currently
`true` for all passes).

`[Size]` is not. `[Size = ViewportContext::frame_size]` is a structured single
atom, but the arithmetic forms are still raw backticks:

```
[Size = `ivec2((builder.graph->get_context<Table::ViewportContext>().frame_size.x + 15) / 16, ...)`]
```

So the **structural** cache key is provable today, but the **allocation** key
(which needs `ViewportContext::frame_size` / `upscale_size`) is not.

**Do:** extend `cond_op` with `PLUS MINUS DIV MOD POW` and a comma, so
arithmetic size expressions parse as term sequences like conditions do, then
migrate the `[Size]` backticks. The existing renderer already handles
`function_id` (`ivec2(...)`, `Math::DivideByMultiple(...)`), so most of the work
is grammar plus migration.

**Test it the same way:** snapshot `autogen/` before, migrate, regenerate, and
require a byte-identical diff. That is what made the condition migration
trustworthy — the renderer's spacing rules (single space around binary
operators, tight after `!` and `(`) exist specifically so any difference in
output is a real difference in meaning rather than whitespace.

---

## 7. Stale output is never cleaned

The generator writes files but never removes ones it no longer produces.
Deleting a `PassNode` leaves its `autogen/pass/<Name>.h` behind forever; seven
such orphans accumulated (`CopyPrev.h`, `GBuffer.h`, `RTXPass.h`,
`ShadowDenoiser_*.h`, `VSM_RenderPage.h`) before being removed by hand. They
are invisible to the build (nothing includes them) but they mislead anyone
reading the tree — those files were the last ones still showing the
pre-migration `setup_func` member, which made the pass-setup migration look
incomplete when it was finished.

**Do:** track every path written during a run, then delete files in the managed
output directories that were not written. Guard it so it only ever touches
known-generated directories, and only files carrying the DO-NOT-EDIT banner.

---

## 8. Smaller items

- **`Parsed::merge` (`Parsed.h:977`) does not detect collisions.** It is a plain
  `container.splice` (`my_container::merge`, `Parsed.h:170`), and `find()`
  returns the *first* match — so two `.sig` files declaring the same struct or
  pass name both end up in the list and the winner is decided by directory
  iteration order. Silent, and not reproducible across machines if the
  filesystem enumerates differently. Should be a diagnostic naming both source
  files.
- **Codegen mutates the parsed model.** `render_condition_options`
  (`Main.cpp:217`) writes rendered C++ back into `value_atom.expr`. The design
  invites this (reflection happens afterwards), but it means "as parsed" and
  "as resolved" are the same object, so nothing can inspect the original form
  later. A separate lowered model is the conventional shape; low priority.
- **`output.txt` is committed noise.** One line, containing a shell error from a
  mistyped `sigparser.exe` invocation. It is git-tracked and is not an input to
  anything. Delete it.
- **`generate_sigs.bat` regenerates the ANTLR parser, not the sig output.** The
  actual generator is `sigparser.exe` run from this directory. The name invites
  the wrong assumption; either rename it or have it do both.

---

## Suggested order

1. **Item 1** (error listener + fail the run) — ten lines, removes the worst
   failure shape.
2. **Item 2** (source locations) — unblocks all diagnostics.
3. **Item 3** (validate pass), starting with the option-name whitelist, which
   catches the one class of mistake that can change rendering with no compile
   error.
4. **Item 4** (`get_elem` assert) — one line, prevents the next contributor
   from hitting a null deref.
5. Items 5–8 as they become relevant.
